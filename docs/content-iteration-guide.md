# AIOS101 内容迭代与工程维护指南

版本：v0.1；日期：2026-10-28。基于网站 v0.4 当前实现核对。

上游：[课程总规格](../specs/course-spec.md)、[协作规范](../specs/collaboration-spec.md)、[验收规范](../specs/acceptance-spec.md)、[体验基线](learning-experience-baseline.md)。本指南落实已有规则，不替代章节和活动规格。

## 1. 分工与日常编辑入口

内容制作方负责学习目标、解释、真实材料、活动设计和内容评审；数字资源维护方负责内容接入、交互适配、兼容、自动检查和发布核验。维护者判断课程方向与教学发布范围。

| 要修改什么 | 编辑入口 | 当前网站如何响应 |
|---|---|---|
| 绪论、章节正文 | textbook/preface.md、textbook/chapters/ | 构建后自动更新全文、目录、检索和阅读估时 |
| 新增 CH01—CH12 范围内章节 | 同一目录中唯一的 CHxx-*.md | 自动进入课程地图和阅读器；不会自动制作定制活动 |
| 章节目标或内容边界 | specs/chapters/ | 先同步相关教材、活动和评价；不是单纯文案修改 |
| 任务、反馈、学习产物 | activities/ 中的规格与学生/教师材料 | 正式交互字段需由维护方同步；Markdown 更新不自动重写表单 |
| 来源与版本 | specs/source-register.md、正文中的来源链接 | 来源登记和链接随构建发布，结论仍需人工核验 |
| 插图、视频、公式、新附录或新组件 | 对应资源目录与规格 | 需检查渲染和构建接入，不能假定上传即显示 |

不要维护第二份网页正文，也不要手工修改生成目录 dist/。日常作者无需修改 CSS 或 JavaScript。新增和调整活动时，作者交付教学内容，数字维护方承担配置和实现。

## 2. 当前内容格式约定

- 正文第一行使用一级标题，保留章号；文首使用现有的“> 版本：”与“> 状态：”格式。
- 二级标题划分阅读小节，三级及以下标题用于节内结构。同章二级标题应唯一；“关键术语”保持现有标题和条目格式，便于提取。
- CH、ACT、EVD、SRC ID 不复用；调整标题不应顺便改动这些 ID。章节文件保持 CHxx-*.md 命名，同章只保留一份正文正本。
- 当前渲染器支持常用段落、标题、简单列表、表格、引用、链接和代码块，并非完整 Markdown 扩展实现。复杂嵌套列表、公式、脚注和内嵌组件需预览确认。
- 当前图片 Markdown 被处理为链接，textbook/assets/ 也没有通用复制接入；正式配图需要同时完成网页渲染与资源发布，不能仅替换图片占位后宣称已经展示。
- 正文给出概念、案例、边界和思考；长操作步骤、填写区域和评审要求放在独立任务单，沿用打印教材与数字资源的职责划分。

## 3. 特别注意已有学习记录

当前小节锚点由二级标题计算得到。改写标题会改变锚点，旧书签可能无法定位，旧笔记仍在手账中但与新小节的关联可能失效。因此标题更名、拆节、并节要列为结构变更，交给维护方处理映射；不能要求作者为了兼容而永远保留错误标题。

活动输入按活动 ID 和字段 ID 保存。字段改名、删除或改变含义，需要明确旧答案怎样保留、怎样展示以及是否适用于新版任务。上线前检查旧备份恢复。页面部署回滚不会自动回滚浏览器中的学习数据。

未来应加入独立且持久的小节 ID、内容/活动版本映射和迁移测试；当前尚未完成。

## 4. 以一个章节作为可评审交付单元

每章逐步补齐下列内容，并分别标明状态；正文先提供草稿阅读时，不把整章称为教学就绪。

1. 章节规格：核心问题、目标学习者、学习成果、范围、误解和验收条件。
2. 教材正文：来源明确的解释、案例、小结和思考；重要判断有证据边界。
3. 材料与视觉：固定版本、读取日期、图题、替代文本、来源、许可与可用的替代材料。
4. 探究活动：问题、输入、步骤、预期产物、反馈依据、修订机会、未知项与静态路径。
5. 教学支持：教师指南、量规、常见困难与实际试学记录。
6. 发布说明：本次改变、影响的下游、已验证项目、未决项与负责人。

同一课程最低证据不因网页形式改变而省略。进阶任务不得成为全员核心路径的设备或编程门槛。反馈解释应帮助推理，不自动替学习者编造答案或同伴意见。

## 5. 小步变更与发布流程

建议以一章或一个具体问题建分支和 PR：明确工作项与完成条件 → 修改相关正本 → 自动检查 → 内容评审和浏览器预览 → 合并 main → 核验部署与发布记录。

错字和链接修复采用轻量流程；改变核心概念、案例、活动或评价时检查下游，实质目标或范围变化先更新相应规格。课程定位和成果变化按上游规范处理。

当前 main 上满足路径条件的提交会自动部署 Pages。即使正文状态写“草稿”，只要文件位于构建扫描目录中，也会成为可读页面。尚不准备提供网站阅读的内容应留在工作分支/PR；公共仓库中的工作分支仍然公开，不能存放受限材料。

当前 PR 工作流运行检查并构建产物，没有自动为每个 PR 创建独立可访问预览站。可以由维护方提供本地或既有私有预览。分支保护、强制评审和必过检查应作为后续仓库设置建设项，不声称当前已强制启用。

## 6. 分开内容质量与工程质量

| 检查 | 责任与完成证据 |
|---|---|
| 技术检查 | 当前 Actions 检查结构/链接、完整正文、JS 语法、数据迁移与恢复、品牌资产和构建；保留运行记录 |
| 来源与教学检查 | 人工阅读来源，核对版本、对象、样本、分母、事实/推断/模拟及量规对齐 |
| 体验检查 | 变更页在桌面和小屏可读可操作；关键导航、批注、活动保存与导出不退化 |
| 学习效果 | 小规模真实试学，记录误解、卡点、任务负担、产物和反馈后的修订 |

自动检查不能证明教学效果，也不自动验证所有外链、图片授权或事实。基线版本仍有常用浏览器下载落盘、完整无障碍、真实设备、并发多标签编辑等未完成项，见[实际核验记录](../specs/learning-review-record.md)。

来源引用优先绑定固定提交、版本或文档日期。动态 Issue/PR 标明读取日，替换案例时同步观察窗、活动说明、反馈解释与静态任务单。不要把“更新日期”改成今天就视为已重新核查。

## 7. 提交说明的最小内容

每次迭代说明对应章/活动、修改原因、影响文件、来源版本、是否改动结构或字段、实际检查和待评审问题。可以使用以下工作指令示例：

> CH04 正文已更新。沿用体验基线 v0.4，请检查概念与来源、比较相邻章节术语、生成阅读预览，并根据学生任务单适配交互。注明本次涉及的锚点或旧记录影响、已执行检查和未决项；教学状态按实际评审结果记录。

该示例用于明确当前工作，未来实际发布仍以维护者当次指令及持续授权范围为准。

## 8. 下一轮工程加固：建议顺序，尚未实现

1. **保护持续学习记录**：持久小节 ID、旧标题别名、活动字段版本与迁移回归用例。验收示例：修改一个小节标题后，旧书签、批注和备份仍能对应原内容。
2. **统一章节清单与发布状态**：从配置读取内容版本、阅读/活动状态、入口和发布日期；加入明确发布开关。验收示例：新章可作为草稿阅读，但未完成活动不被标为可用；关闭网站发布的章节不进入导航。
3. **减少活动重复维护**：建立结构化活动内容格式、字段校验和通用组件，逐步从一个活动正本生成任务单和网页。迁移前明确正本和回退方式，不能让 YAML、Markdown 与 JS 同时成为三份相互冲突的正本。
4. **补齐发布检查**：加入图像和公式的资源管线、关键交互浏览器回归、旧数据兼容、按变更范围的预览；对语义来源和教学效果保留人工评审。

先用第三章的一章内容包验证上述工程能力，再复用到后续章节。现有通用组件不能表达某项认知任务时再扩展组件库，避免每章独立开发一套界面。

## 9. 建议的建设节奏

每次迭代聚焦一个章节或一项明确问题。先用现有打样做一次真实试学，验证任务是否过重；再完成第三章配套任务与工程加固，形成首个完整可复用内容包；后续按章推进，每完成一篇做一次术语、来源、活动难度和学习成果的跨章复核。

正文草稿数量、网页数量、活动填写率都不单独作为课程完成指标。更有价值的证据是：学习者是否能解释材料支持什么、不能推出什么，以及收到反馈后是否作出了有依据的修订。
