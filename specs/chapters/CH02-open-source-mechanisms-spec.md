## 1. 章节定位

### 1.1 核心问题

为什么把成果公开，并不等于别人能够复用；为什么参与者很多，并不等于形成有效协作；为什么一个开放项目获得关注，也不能直接证明它产生了公共价值？

### 1.2 本章价值

第一章回答为什么 AI 通识教育需要开源，本章进一步解释开源如何通过具体机制工作。全章以“开放—复用—协作—公共价值”为分析框架，把开源从抽象理念转化为可观察的材料、权利、文档、协作记录、评审、维护与实际受益。该框架为第三章的 AI 开源生态全景建立微观基础，也为第七章开放判断、第九章生态数据研究和第十章社区贡献埋下证据意识。

### 1.3 目标学习者

面向所有学科背景的大学生。不要求编程、许可证或社区经验。针对“公开就是开源”“复制就是复用”“人多就是协作”“下载量就是公共价值”“贡献必须写代码”等先入认识提供概念支架。

### 1.4 建议学习时间

| 部分 | 建议时间 | 说明 |
|---|---|---|
| 教材学习 | 75—100 分钟 | 含概念辨析、真实社区记录与平台背景 |
| 课堂活动 | 45—60 分钟 | 真实仓库观察、协作角色扮演与概念辨析 |
| 探究实践 | 70—90 分钟 | 独立完成机制分析单与模拟贡献方案 |
| 反思与修订 | 15—20 分钟 | 根据同伴评审修订贡献方案和价值证据 |

### 2.3 常见误解与诊断

| 常见误解 | 形成原因 | 诊断问题／任务 | 纠正方式 |
|---|---|---|---|
| 网上可见或免费下载就是开源 | 混淆获取条件与使用、修改、再分发权利 | 能否找到对应对象和明确许可？ | 回到开放定义和具体材料核查 |
| 有了许可就一定能顺利复用 | 忽略文档、格式、依赖、版本和质量 | 新使用者能否理解并验证结果？ | 区分权利可用与实际可用 |
| 人多、Star 多就是良好协作 | 用关注度替代任务、沟通、评审和维护证据 | 谁处理反馈，如何决定合并？ | 观察协作过程而非只看数量 |
| 贡献必须写代码 | 把项目价值缩小为实现功能 | 文档、测试、翻译、设计能否回应需要？ | 用真实贡献类型拓宽参与入口 |
| 公开或高下载自动产生公共价值 | 忽略实际使用、受益者、成本和风险 | 谁受益、谁承担维护与伤害？ | 将开放条件与实际结果分别取证 |

## 4. 内容范围与边界

### 4.1 必须覆盖

- 公开可见、开放授权、实际可复用与协作开放的区别；
- 复用所需的对象、版本、权利、文档、格式、依赖、署名和修改说明；
- 贡献、评审、反馈、决策、发布和维护构成的协作闭环；
- 文档、数据、评测、翻译、设计、讨论和代码等多样贡献；
- 公共价值的受益者、实际使用、可及性、维护成本、风险和持续性；
- 四个环节相互连接但不自动保证下一环节的关系；
- 软件案例向 AI 情境迁移时的材料扩展与类比边界。

### 4.2 可选拓展

- 阅读 Producing Open Source Software 关于信息管理与可分叉性的选段；
- 观察一个真实项目的 README、CONTRIBUTING、Issue 或评审记录；
- 讨论数字公共品标准中的开放许可、文档、隐私和“不造成伤害”等维度。

### 4.3 明确不覆盖

- 开源许可证逐条比较、合规判定或许可证选择教学，留待第七章；
- AI 生态组成和数据供应链全景，留待第三章；
- 社区治理模式、行为准则执行和真实 PR 操作细节，留待第十章；
- 生态指标、下载量或影响力统计方法，留待第九章；
- 对任何现实项目的质量、公共价值或开放程度作未经核查的认定。

### 4.4 稳定内核与时效内容

| 类型 | 内容 | 更新策略 |
|---|---|---|
| 稳定原理 | 开放—复用—协作—公共价值及其证据断点 | 随课程认知框架修订 |
| 官方定义 | OSD、自由软件定义和贡献指南 | 固定读取日期，关键版本变化另增来源 |
| 真实案例 | AIInfra 仓库 README、LICENSE、Issue #386 与 PR #364 | 固定提交或公开记录；报告者主张与项目事实分开 |
| 平台背景 | GitHub、AtomGit 的仓库、Issue、PR 等基本协作概念 | 固定读取日期；只解释必要概念，不在打印正文展开操作步骤 |

## 5. 建议内容结构

1. **问题导入**：从 AIInfra 真实仓库观察材料、许可、文档、Issue 与 PR 分别说明什么；
2. **开放**：从可见到有权使用、研究、修改和分享，区分获取与授权；
3. **复用**：结合仓库体积与发布说明，解释版本、格式、依赖和理解成本；
4. **协作**：解释 Issue、PR、Commit、Branch、Fork、评审与合并，介绍 GitHub 和 AtomGit 的落地场景；
5. **真实记录**：比较一个开放 Issue 与一个已合并 PR，区分问题提出、变更建议和项目决定；
6. **公共价值与关系整合**：从公开和关注转向实际受益、成本、风险与持续性；
7. **思考与延伸**：保留少量开放问题，完整活动放入独立任务单和在线资源。
